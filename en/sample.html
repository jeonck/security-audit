How our review scores on an intentionally vulnerable app

Test target: DVPWA · Thorough mode · about 28 min
What is this test? To measure whether a review actually finds vulnerabilities, you need a target whose vulnerabilities are already known. DVPWA (Damn Vulnerable Python Web Application) is a course-management website built for security training with several intentionally planted vulnerabilities, and its author published which ones are there. We used those five published flaws as the answer key and report exactly how many we found.
Level of this sample: Scan (automated review result)This sample is the output of 34 AI agent calls across six phases, organized as-is.
  • Included: automated six-phase review; verdicts (Confirmed / Needs validation / Not an issue)
  • Not included: human review of each finding, written remediation guidance beyond the automated output, re-review after fixes

  • A human reviewer checks every confirmed finding before delivery
  • For each confirmed finding: the exploit path traced through the code, plus step-by-step remediation guidance
  • One re-review of your fixes to verify they address each finding

3 confirmed findings

▲ High riskWithout logging in, anyone can control the database through an input fieldTechnical term: SQL injection

What can happen? By entering a crafted value in a form field, an unauthenticated user can read every stored user's username and password hash. One request is enough.

How to fix it Use parameterized queries (pass user input as bound parameters, never concatenated into SQL), and require authentication on this endpoint. sqli/dao/student.py:42

● Medium riskA malicious post runs script in other users' browsersTechnical term: Stored XSS

What can happen? Script embedded in an anonymous post executes in the browser of every visitor and admin who views it. It can be used to alter the page, show a fake login prompt or steal session cookies.

How to fix it Enable template autoescaping so posts are rendered as text, not HTML. sqli/app.py:35

● Medium riskGrades, courses and students can be created without logging inTechnical term: Broken access control (missing server-side authentication and authorization checks)

What can happen? The screen shows buttons only to admins, but the server never checks who is asking. Even without the button, a direct request can enter grades. It's like putting a "staff only" sign on a building but leaving the door unlocked.

How to fix it Check on the server that the requester is an admin for each action. sqli/views.py:52,84,135

What this test does not tell you

  • This was a static review: we read the source code and did not run the application. Anything that can only be known by running it is marked separately as "Needs validation".
  • This is the result on one small practice app. Detection rates on your codebase may differ.
  • For three of the five flaws we gave hardening advice only and did not call them separate findings. That is something we need to improve.
